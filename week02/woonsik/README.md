# 5장. 안정 해시 설계

> 서버 증감 시 키 재배치 범위 축소. 해시 링, 시계 방향 탐색, 가상 노드 활용.
>
> 2주차 공유 자료 (약 2페이지) / [코드 실험](examples/README.md) / [검증 퀴즈](quiz.md)

## 1페이지 — 왜 필요하고 어떻게 동작하는가

### 나머지 연산의 문제

`서버 = servers[hash(key) % N]`. 서버 수 N 변경 시 나머지와 담당 서버 대거 변경. 캐시 서버라면 대량 캐시 미스 → 원본 DB 부하 급증 가능.

예: 해시값 0~11, 서버 `[A, B, C]`에 D 추가. `% 3` → `% 4` 변경 시 12개 중 9개 이동. 일반적으로 해시값이 충분히 넓고 균등하며 기존 서버 순서 유지 시, N→N+1의 이동 비율 약 `N/(N+1)`. 모든 키 이동은 아님.

### 해시 링과 담당 구간 [1]

키와 서버를 같은 해시 공간에 배치. 최댓값 다음은 0으로 연결. 키 위치 이상인 첫 서버 선택, 없으면 첫 서버로 순환. 서버 S의 담당 구간: `(직전 서버, S]`.

```text
시계 방향 증가, 99 다음 0으로 순환
0 ── A:10 ── key:20 ── B:40 ── C:80 ── key:90 ── 99 ↺
                └→ B                          └→ A
D:30 추가 → (10,30]만 B에서 D로 변경. key:40은 B 유지.
B:40 제거 → 기존 B 담당 구간만 다음 서버 C로 변경.
```

가상 노드 사용 시 한 물리 서버가 여러 구간 담당. 신규 서버 추가 시 여러 기존 서버에서 일부 구간 인계. 기존 토큰 위치 유지가 재배치 국소성의 전제.

### 이동량 비교

| 변경 | 나머지 연산 | 안정 해시 |
|---|---|---|
| N→N+1 추가 | 균등 해시 가정 시 약 `K × N/(N+1)` 이동 | 새 서버 담당 키만 이동. 기대량 `K/(N+1)` |
| N→N−1 제거 | 인덱스와 나머지 변경으로 광범위 재배치 가능 | 제거 서버 담당 키만 이동. 기대량 `K/N` |

K는 전체 키 수, N은 변경 전 물리 서버 수. 키와 토큰을 균등하게 해싱하고 모든 서버에 같은 수의 토큰을 배치한다고 가정. 실제 이동량은 담당자가 바뀐 구간의 키 수. 3→4대 증설 실험에서 기대 이동률 25%, 실제 이동률 22.79%(서버당 토큰 128개).

## 2페이지 — 가상 노드와 설계 한계

### 가상 노드: 한 서버에 여러 좌표 [2, §4.2]

`A#0, A#1, …, A#V-1`을 각각 해싱하고 실제 목적지는 A로 매핑. 큰 구간 하나에 좌우되던 부하를 여러 작은 구간으로 분산. V 증가 시 일반적으로 서버별 점유율 편차 감소. 모든 배치에서 단조 개선 보장은 없음.

- 용량 큰 서버: 더 많은 토큰 할당으로 가중 분배 가능.
- 전체 토큰 수 `M = N × V`. 물리 서버 3대에 토큰 128개씩 배치하면 `3 × 128 = 384`개.
- 링 메모리 `O(M)` — 토큰마다 좌표와 담당 서버를 저장. 메모리는 토큰 수에 비례.
- 링 조회 `O(log M)` — 균형 트리에서 키의 해시 좌표 이상인 첫 토큰을 탐색. 없으면 링의 첫 토큰으로 순환.
- **가상 노드 ≠ 복제본.** 좌표 증가만으로 데이터 사본 생성 불가.
- **키 수 균등 ≠ 요청량 균등.** 단일 인기 키는 여전히 한 담당 서버에 집중.

### 코드의 핵심

```java
var entry = ring.ceilingEntry(hash(key)); // 같은 좌표 포함
return (entry != null ? entry : ring.firstEntry()).getValue();
```

[실험](examples/README.md)에서 동일한 10만 키로 `% N`, 토큰 1개, 토큰 128개 비교. 이동 비율, 서버별 키 수, 변동계수 `CV=표준편차/평균` 관찰. CV로 서버별 키 수 편차 측정.

### 핫 키 읽기 분산

같은 값을 접미사가 다른 키(`template:42#0`~`template:42#7`)에 저장. 서로 다른 물리 서버에 배치됐는지 확인. 읽기 요청마다 사본 하나를 선택해 부하 분산. 원본 변경 시 사본 무효화 또는 일괄 갱신. 모든 사본에 쓰는 방식은 *fan-out on write*.

### 운영에서 별도 설계할 항목

| 상황 | 필요한 설계 |
|---|---|
| 클라이언트마다 다른 링 | 멤버십과 링 버전 전파, 전환 중 이전 담당자 조회 또는 요청 전달 |
| 새 담당 서버에 데이터 없음 | 캐시 미스 후 원본 조회 및 점진적 예열. 영속 저장소는 복사, 변경분 동기화, 라우팅 전환 순서로 처리 |
| 서버 장애 또는 데이터 유실 | 장애 감지, 복제, 복구 정책. 복제 대상은 서로 다른 물리 서버 선택 [2, §4.3] |

안정 해시는 **담당 위치 결정 규칙**. 데이터 자동 이동, 복제, 강한 일관성은 별도 설계. 링 변경만 배포하면 기존 데이터 접근 실패 또는 캐시 미스 급증 가능.

**1분 설명** — `% N`의 재배치 문제 → 링의 담당 구간 → 가상 노드의 편차 완화 → 핫 키 대응과 데이터 이전 설계.
